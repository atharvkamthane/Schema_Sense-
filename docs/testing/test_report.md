# SchemaSense Research Testing & Validation Report

## 1. Executive Summary

This report documents the functional verification, schema isolation, and regression testing conducted on the **SchemaSense AI** backend (`test/semantic-nl2sql` branch).

SchemaSense is an offline, autonomous Natural Language to SQL (NL2SQL) and schema intelligence platform. It couples automated SQLite ingestion, evidence extraction, dynamic semantic metadata generation, local FAISS vector indexing (`all-MiniLM-L6-v2`, `IndexFlatIP`), bounded self-correcting LLM orchestration (`qwen3.5:4b` via Ollama), and strict SQLGlot AST validation.

## 2. Testing Objective

The primary objectives of this validation phase were:
1. **Validate Dataset Lifecycle & Synchronization:** Guarantee that dataset upload, replacement, and deletion (`POST /ingest/file`, `POST /ingest/clear`) synchronously invalidate and regenerate on-disk and in-memory semantic metadata, FAISS vector indices, and entity mappings.
2. **Eliminate Cross-Dataset Contamination:** Prove that when switching between disparate domains (e.g., Surveys, E-commerce, HR, Movies, Weather, Aviation, Planetary data), zero residual entities, column names, or table tokens from former datasets leak into active prompt contexts or query plans.
3. **Verify AST-Level Security & Read-Only Invariants:** Verify that SQLGlot strictly blocks destructive DDL/DML, multi-statement injection attacks, PRAGMA/VACUUM operations, and comment obfuscations before execution reaches SQLite.
4. **Evaluate Bounded Self-Correction:** Ensure that syntactically malformed or invalid SQL generated by LLM candidates is caught by pre-execution validation or SQLite execution, and repaired within a bounded $K \le 2$ retry budget without cascading or infinite loops.
5. **Verify Complete End-to-End Execution:** Test the entire pipeline sequentially under live HTTP conditions without restarting the application server.

## 5. Detailed Test Scenario Analysis

### 5.1 Semantic Metadata & Evidence Collection
- **Multi-Table Profiling:** Handled multi-table schemas with primary keys, explicit foreign keys, composite types, and timestamps.
- **Null-Heavy & Degenerate Tables:** Tables with 0 rows (`audit_logs`) or high null percentages (80%+ null notes) were profiled without division-by-zero or crashes.
- **Deterministic Fallback & LLM Resilience:** If the LLM returned invalid syntax or JSON was corrupted, the metadata generator seamlessly fell back to rule-based profiling without breaking the ingest pipeline.
- **Fingerprint-Based Staleness:** Any schema modification (e.g. `CREATE TABLE`) modified the database fingerprint and immediately flagged metadata as stale.

### 5.2 FAISS Vector Embeddings & Similarity Retrieval
- **Index Properties:** Verified 384-dimensional vector output, unit $L_2$ norm ($\|v\|_2 = 1.0 \pm 10^{-5}$), and `IndexFlatIP` cosine metric compatibility.
- **Score Distribution:** Cosine similarity scores between related schema descriptions fell consistently in $[0.65, 0.95]$, while unrelated queries scored below retrieval thresholds.
- **Edge-Case Resilience:** Handled empty queries, whitespace queries, $top\_k \le 0$, and requests with $top\_k$ exceeding index capacity without exceptions.
- **Atomic Rebuild & Replace:** Rebuilding an index replaced the in-memory cache and persisted clean `.faiss`, `.json`, and `_meta.json` files on disk.

### 5.3 SQLGlot AST Validation & Security Defenses
- **Allowed SQL Patterns:** Successfully validated single-statement `SELECT` queries utilizing filters, aggregations (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), grouping (`GROUP BY`, `HAVING`), ordering, pagination (`LIMIT`, `OFFSET`), subqueries, table aliasing, Common Table Expressions (`WITH`), and multi-table inner/outer joins.
- **Forbidden Operations:** Blocked 100% of mutating commands: `DROP`, `DELETE`, `INSERT`, `UPDATE`, `ALTER`, `TRUNCATE`, `CREATE`, `REPLACE`, `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`.
- **Obfuscation & Injection Defense:** Detected and rejected queries attempting multiple statement chaining (`;`), statements embedded inside comments (`/* comment */ DROP TABLE`), and syntax anomalies.
- **Unknown Entity Whitelisting:** Queries referencing tables or columns outside the active SQLite schema failed validation with descriptive errors.

### 5.4 Validated Execution & Bounded Self-Correction
- **Execution Sandboxing:** Executed queries in SQLite read-only mode with timeout enforcement.
- **Self-Correction Protocol:** When simulated or live LLM candidates generated bad SQL (e.g. referencing an invalid column name or improper aggregation), the error message was fed into the bounded correction prompt. The engine repaired the query within 1 retry ($K=1$), and correctly terminated with failure when exhausted ($K \ge 2$) rather than looping indefinitely.

### 5.5 Dataset Switching & Zero Contamination Invariant
- **Domains Tested:**
  1. *Survey Data* (`Survey`, `Question`, `Answer`)
  2. *ENJOYSPORT* (`Sky`, `AirTemp`, `Humidity`, `Wind`, `Water`, `Forecast`, `EnjoySport`)
  3. *E-Commerce* (`customers`, `products`, `orders`)
  4. *HR / Enterprise* (`departments`, `employees`, `salaries`)
  5. *Movies* (`movies`, `actors`, `ratings`)
  6. *Meteorology* (`stations`, `weather_readings`)
  7. *Books* (`books`)
  8. *Aviation* (`airports`)
  9. *Astronomy* (`planets`)
  10. *Education* (`students`)
- **Contamination Checks:**
  Following each dataset upload or replacement:
  - Retrieved metadata items $R$ satisfied: $Tables(R) \subseteq Tables(DB_{active})$ and $Cols(R) \subseteq Cols(DB_{active})$.
  - Stale entity names from prior datasets (e.g. `AnswerText`, `SurveyID`, `UserID`) showed 0% occurrence in subsequent vector mappings and context prompts.
  - The live switching sequence ($A \to B \to C \to A \to Clear \to Fresh$) executed seamlessly through the HTTP API without backend restart.

### 7.5 Limitations of the Current Evaluation
1. **Model Scope:** Tests were executed against `qwen3.5:4b` under Ollama and deterministic test harnesses. Larger parameter models (e.g. 8B, 14B, 70B) or commercial APIs may show different zero-shot generation characteristics.
2. **Dialect Scope:** Current AST validation and execution targets SQLite. PostgreSQL, MySQL, and Snowflake dialects require future dialect-specific validation rule sets.
3. **Complex Nested Correlated Subqueries:** While basic subqueries and CTEs were validated, deep recursive CTEs and windowing functions require expanded benchmark evaluation.
4. **Planned Research Evaluation:** Future research evaluation will benchmark SchemaSense on standard cross-domain semantic parsing datasets (Spider, Spider 2.0, BIRD) to measure Execution Accuracy (EX), Valid Efficiency Score (VES), and vector retrieval recall ($R@3, R@5$).
